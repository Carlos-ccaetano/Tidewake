# ADR 0018: Project ownership

- Status: accepted
- Date: 2026-10-25

## Current implementation status

Project ownership and project-bound API authentication are implemented. The [ownership migration](../../priv/repo/migrations/20261030074028_scope_webhook_resources_by_project.exs) preserves legacy ownership, requires non-null project references and enforces composite Delivery relationships to same-project Event/Endpoint records; event external IDs are unique per project. Ownership is immutable through supported application operations. [Scope](../../lib/tidewake/projects/scope.ex) comes from persisted service-account authentication, and [HTTP isolation tests](../../test/tidewake_web/controllers/api_isolation_regression_test.exs) cover trusted project lookup and non-disclosing 404s. There is no static-token or implicit legacy-scope HTTP fallback.

Admin manual retry POST and audit GET resolve Delivery within trusted project scope, including replay and every page. See [authentication operations](../api/authentication.md) and the [retry contract](../api/manual-retries.md). Human identity/UI, HTTP credential management, audit retention/deletion, receiver `Retry-After` handling and production deployment remain pending; Ironhold is unchanged. The context and decision below retain their historical wording.

## Context

Tidewake currently stores endpoints, events, and deliveries globally. They use generated integer primary keys; `events.external_id` has a global unique index, and deliveries have restrictive foreign keys to events and endpoints plus uniqueness on `(event_id, endpoint_id)`. Attempts and manual retry audit records reference a delivery. None of these resources has project ownership yet.

The HTTP controllers use global context lookups and the shared Bearer token from ADR 0010. The delivery status API in ADR 0007 exposes a limited representation, but filtering fields does not establish object-level authorization. The internal manual retry core from ADRs 0015–0017 is implemented without an attributable authenticated principal or an operational entry point.

Attributable credentials need an ownership boundary before the API can isolate callers. A delivery assembled from an event and endpoint belonging to different projects must be invalid even if an application check is omitted or competing transactions race.

## Decision

Use `Project` as the ownership boundary for endpoints, events, and deliveries. Every such resource belongs to exactly one project after migration, and its ownership is immutable. A request's project must come from trusted authenticated server context. PostgreSQL is the final authority for same-project delivery references; application authorization remains necessary for every HTTP operation.

This ADR defines a future persistence and lookup contract. It changes no schema, migration, context function, worker, authentication plug, controller, route, response representation, or public API. The current shared token and global behavior remain the implemented baseline until the separately reviewed migration and authentication cutover.

The association of `ServiceAccount` with `Project`, credentials, and trusted scope construction will be defined in the next ADR. This decision supplies no role matrix or credential format.

## Data model

### Project

Retain the repository's generated integer `id` convention for internal primary keys and matching foreign-key types. Add a separate stable UUID `public_id` for operational project references; it does not replace existing resource IDs or change HTTP paths in this ADR.

| Field | Contract |
| --- | --- |
| `id` | Generated internal primary key; never selected by an API caller. |
| `public_id` | Required, globally unique UUID, generated by trusted code once and immutable thereafter. |
| `slug` | Required, unique canonical slug of 1–63 ASCII bytes: lowercase letters and digits, with single hyphens separating nonempty segments. |
| `name` | Required, nonblank UTF-8 display name bounded to 255 bytes; carries no permissions. |
| `status` | Required bounded string, exactly `active` or `suspended`; initially `active`. |
| timestamps | UTC insertion and update timestamps with microsecond precision. |

Uniqueness, nullability, and the bounded status vocabulary must be backed by database constraints and matching changeset validation. Slug and name bounds must also be validated before persistence. Names and slugs are descriptive values; the stable UUID is the operational identity.

Reserve one project with slug `legacy` for all existing global data. Create it once during migration and retain its generated `id` and `public_id`. Migration retries must reuse the recorded legacy identity rather than generate a replacement; an unexpected collision with the reserved identity must stop the migration. Do not infer the legacy project from the first row in `projects`, from a request parameter, or from a new value generated on application startup.

### Owned resources and history

Add required `project_id` references to `endpoints`, `events`, and `deliveries`, using the same internal key type as `projects.id`. Set ownership from the trusted project on resource construction, outside caller-cast attributes. Delivery ownership is derived from its event and must match its endpoint.

Replace the global event uniqueness rule with `UNIQUE (project_id, external_id)`. The same `external_id` may identify independent events in two projects; reuse inside one project remains a conflict. Preserve the existing validation and exact value of `external_id`, including its case. Lookups by external ID must include the project.

Keep the existing delivery uniqueness on `(event_id, endpoint_id)`, because those IDs remain globally unique. Preserve lifetime attempt numbering, cycle constraints, timestamps, and append-only history. Attempts and manual retry audit records inherit ownership through their restrictive delivery relationship; this ADR requires no duplicate project column on either history table. It does not rewrite historical actor subjects, key digests, or version-1 retry fingerprints from ADR 0017.

## Ownership invariants

1. `Endpoint.project_id`, `Event.project_id`, and `Delivery.project_id` are non-null after backfill. Context constructors obtain them from trusted server context; changesets do not allow caller attributes to choose or replace them.
2. Ownership is write-once after migration. Updates and internal context operations must reject reassignment, including endpoint edits. There is no project-transfer operation. Foreign keys enforce relational consistency, while trusted construction and update validation enforce this application-level immutability; a foreign key alone does not forbid every ownership change.
3. A delivery's project equals both its event's project and its endpoint's project. Use the following database structure with matching column order:

   | Table | Constraint |
   | --- | --- |
   | `endpoints`, `events`, `deliveries` | `project_id REFERENCES projects(id) ON DELETE RESTRICT` |
   | `events` | `UNIQUE (project_id, id)` as a composite reference target |
   | `endpoints` | `UNIQUE (project_id, id)` as a composite reference target |
   | `deliveries` | `FOREIGN KEY (project_id, event_id) REFERENCES events(project_id, id)` |
   | `deliveries` | `FOREIGN KEY (project_id, endpoint_id) REFERENCES endpoints(project_id, id)` |

   The composite foreign keys use restrictive deletes and no cascading owner updates. Keep the existing simple delivery foreign keys restrictive as well. All participating delivery columns are required, so nullable foreign-key components cannot bypass equality. Separate foreign keys on three valid IDs would not prove that they belong together. Composite unique targets and foreign keys provide the cross-table guarantee described in the [PostgreSQL constraints documentation](https://www.postgresql.org/docs/16/ddl-constraints.html#DDL-CONSTRAINTS-FK).
4. Deleting a project with owned resources is restricted. Event and endpoint deletes cannot remove deliveries, and delivery deletes cannot remove attempts or audit history. Suspension or endpoint deactivation preserves ownership and history; neither moves records nor authorizes destructive cleanup.
5. Ingestion selects only active endpoints from the trusted event project, ordered by increasing ID. Event insertion, same-project delivery fan-out, and initial jobs remain one transaction. Zero eligible endpoints remains valid. Direct scheduling must enforce the same ownership equality, with database constraints protecting races and bypassed checks.
6. Internal delivery, retry, and recovery workers continue resolving persisted work by `delivery_id`. They trust database-protected relations and preserve the delivery-then-endpoint lock order and existing attempt/cycle guards. Project identity is derived from the delivery when needed, not accepted as a second source of truth in job arguments. This decision does not add suspension-based cancellation of queued deliveries.

## Migration and compatibility

Use new migrations only. Do not edit applied migrations or renumber existing records. Each implementation PR must leave `main` deployable with its migrations, writers, readers, and tests in agreement.

1. Create `projects` with the required identity and metadata constraints.
2. Create the single stable legacy project. Provisioning this row does not create credentials or grant a caller access to it.
3. Add `project_id` in a staged migration and backfill all existing endpoints and events to the legacy project, then deliveries to the same project. Retain all resource IDs, relationships, event content, attempts, audit evidence, and pending jobs. Coordinate write quiescence or trusted compatibility writers so new rows cannot escape the backfill. Any temporary default must refer only to the recorded legacy project.
4. Build and validate event uniqueness on `(project_id, external_id)` before removing the old `events_external_id_index`. Update the changeset constraint mapping and external-ID lookup contract in a coherent implementation PR. Never drop the global index before its replacement exists; prevent other-project writes while any externally reachable lookup still assumes global uniqueness.
5. Add the simple project foreign keys, composite parent unique targets, and composite delivery foreign keys. Validate existing relationships and stop on missing ownership or cross-project references; do not repair mismatches by moving or deleting history. Preserve the existing restrictive foreign keys throughout.
6. Verify the backfill and concurrent-write strategy, then enforce `NOT NULL` for ownership. Nullable ownership is a migration phase, never an authorized HTTP scope or a permanent runtime fallback. Prove cross-project rejection through direct database writes as well as context tests in the implementation PRs.
7. Keep compatibility bounded until authentication is activated. A temporary legacy wrapper must select the legacy project in trusted server code and scope every lookup to it. The shared token must never select an arbitrary project. Do not enable multiple-project resource traffic while old global HTTP reads remain reachable. Prove fan-out isolation, same-project idempotency conflicts, and independent external IDs across projects before enabling that traffic.
8. At project-scoped authentication cutover, remove shared-token compatibility, implicit legacy scope, temporary ownership defaults, and HTTP access through unscoped context helpers. Missing trusted scope must deny access rather than select the legacy project. Retain only the internal ID-based operations required by workers. Verify all existing routes after cutover; a rollback must not reintroduce global HTTP access to a database containing several projects.

Historical manual retry evidence remains unchanged throughout this migration. Any future change to its canonical request identity requires the explicit versioning and replay-compatibility decision required by ADR 0017.

## Authorization boundary

After the separate authentication cutover, every HTTP query and mutation must begin with the authenticated project's trusted scope. This includes endpoint listing and updates, event ingestion and external-ID lookup, individual retrieval, event delivery status, and future retry or audit operations. Load the parent event inside that scope before listing its deliveries. Construct writes from the scoped project and scoped related records; never load globally first and return a record before checking ownership.

Numeric IDs, UUIDs, slugs, and caller-provided project fields grant no authority. A project header or URL parameter cannot override the authenticated project. Role checks are additional to project isolation and will be defined separately. Requests without a valid trusted scope, including a scope for a suspended project, fail closed; their credential/error contract belongs to the following identity and API decisions.

For an authenticated caller, an otherwise valid identifier outside its project and an absent identifier produce the same resource-specific `not_found` response. Preserve the existing 404 error shapes, such as `Event not found` and `Endpoint not found`, without revealing a foreign project's existence or identifiers. Do not perform a global existence probe to distinguish these cases. An existing scoped event with no deliveries still returns the empty success list from ADR 0007.

Future manual retry and audit reads must authorize the scoped delivery, including replays, before resolving or disclosing protected audit evidence. The existing internal actor struct is not authentication. [OWASP API1:2023](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/) identifies object access checks as necessary even when IDs are UUIDs; the [Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) supports default denial and permission validation on every request.

## Security and privacy

Ownership is protected operational data. Do not add `project_id`, the project UUID, slug, or name to Telemetry events, measurements, metadata, tags, or ordinary error logs. Continue using bounded outcomes and reasons. Constraint and query failures must be mapped to controlled responses without serializing database parameters, changesets, or raw errors containing project identity.

Keep current delivery job arguments limited to the existing delivery and attempt/cycle identity. No project field is needed there because the delivery relationship already carries ownership. Credentials, payloads, endpoint URLs, actor subjects, and audit digests remain excluded under the existing confidentiality rules.

Project identifiers may be used only where an explicitly authorized operational contract needs them. Their availability never substitutes for authorization. PostgreSQL integrity protects persisted relationships; it does not prove the caller's identity or permission to read or modify them.

## Consequences

- Resource ownership and event idempotency have one explicit scope, and a database constraint rejects cross-project delivery construction even under concurrency.
- Existing internal IDs, worker arguments, immutable attempt history, and manual retry evidence remain usable.
- Composite reference targets add indexes, and every HTTP data path and fixture needs a scoped counterpart before cutover.
- The legacy project preserves global data without inventing historical identities, but compatibility must be removed at activation rather than becoming an authorization fallback.
- Project-local event IDs do not change outbound envelopes or a receiver's independent deduplication rules. Ironhold remains a separate system with its existing contract.
- Ownership alone does not deliver an authenticated API; identity, administrative permissions, credential lifecycle, and authorized audit access remain subsequent work.

## Alternatives considered

| Alternative | Reason for rejection |
| --- | --- |
| Treat the shared token or actor subject as ownership | Neither provides a trustworthy project relationship or attributable project authorization today. |
| Rely on opaque UUIDs or controller checks alone | Knowing an ID does not authorize access, and application omissions must not permit inconsistent delivery references. |
| Add only independent foreign keys | Existing event, endpoint, and project rows could still belong to different projects. |
| Check other tables from a `CHECK` expression | PostgreSQL foreign keys express the required cross-table invariant; row checks are not the authority for it. |
| Keep global event external-ID uniqueness | Independent projects would conflict over caller-defined identifiers. |
| Make ownership optional, mutable, or caller-selected | Missing or reassigned scope would make resource access and historical attribution ambiguous. |
| Duplicate project identity in every job and history row | Redundant identities can diverge from the delivery relationship and expand disclosure without a current execution need. |
| Cascade project deletion | It could erase delivery, attempt, and audit history. |

## Out of scope

- migrations, schemas, backfill execution, indexes, triggers, or context implementation;
- service-account association details, credential issuance, rotation, revocation, or human identity;
- role matrices, authentication cutover implementation, route or response changes;
- public manual retry, audit retrieval, operational UI, rate limiting, or retention;
- changes to retry budgets, fingerprints, signing, transport, recovery, or worker job formats;
- receiver deduplication changes, Ironhold changes, deployment, or production rollout.
